# 工作流与文档留痕规范

> 本文是项目长期维护的可见版工作流。项目越大，越不能依赖单次对话记忆，必须通过代码、测试和文档共同交接。

## 工作流总览

```text
需求
  ↓
读取 progress / task_plan / implementation_plan / checkpoint
  ↓
确认 git 状态和最近变更
  ↓
按关键词定位入口
  ↓
追踪调用链、状态、契约和失败路径
  ↓
读取相关测试
  ↓
提出修改范围和验证方案
  ↓
实施最小必要修改
  ↓
运行针对性测试和必要的集成测试
  ↓
检查 diff 和工作区
  ↓
更新进度或交接文档
  ↓
输出完成报告
```

## 维护要求

- 优先更新已有进度、计划和 checkpoint 文档，不重复建立同义文档。
- 重要决策、失败原因、测试证据和暂停位置必须写下来。
- 文档记录应包含日期、范围、结果和下一步，避免只写“已完成”。
- 文档与代码不一致时，先指出差异，再以代码和测试验证实际情况。
- 不因任务简单就跳过留痕；简单任务可以使用简短记录，但不能完全没有记录。

## GitHub / 官方资料调研

遇到新功能、架构设计、技术选型、第三方接入或实现方式不确定时，执行以下步骤：

1. 查官方文档、官方仓库和相关规范；
2. 按相关性和维护状态选择真实存在的相关开源项目进行对比；
3. 阅读核心源码、接口、错误处理和测试，不只看 README；
4. 核对 License、版本状态、已知限制和安全风险；
5. 记录哪些内容可直接复用、哪些只能借鉴；
6. 结合本项目现有代码和测试，确定复用、借鉴或自研方案；
7. 将调研结果写入 `implementation_plan/research/` 或 `docs/research/`。

简单局部修复、纯文档修改、简单配置调整和已有内部实现的直接延续可以跳过，但要在进度或完成记录中写明跳过理由。
