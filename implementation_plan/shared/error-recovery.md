# 错误恢复、Agent/API 故障、崩溃与重启

> 定稿日期：2026-09-18  
> 状态：规划阶段；未经用户明确要求，不编写功能代码。  
> 适用范围：DeepSeek/Agent 网络与 API 故障、电脑任务执行中的程序崩溃、Agent 崩溃、电脑重启、进程异常退出以及无法确认最终结果的中断。

## 1. 核心原则

崩溃或重启后，系统不得自动续跑，不得复用旧计划、旧确认或旧授权。恢复判断必须以电脑当前真实状态为准，审计记录、冻结计划和执行结果只能作为检查线索。

```text
程序/Agent 崩溃或电脑重启
→ 停止自动执行
→ 使旧计划与旧授权失效
→ 读取审计记录和冻结计划作为线索
→ 使用受限只读工具重新扫描电脑当前真实状态
→ 对每个动作分类：已完成 / 未完成 / 状态不确定
→ 向用户展示恢复报告
→ 用户决定是否重新规划
→ 创建新计划或新版本
→ 重新预检
→ 重新授权
→ 才能执行
```

闲聊和实时语音监听可以恢复为普通对话状态，但中断前的电脑任务不能自动恢复为可执行状态。

## 2. 恢复状态分类

每个原计划动作只能标记为以下三类之一：

- `completed`：根据当前真实状态能够验证动作已经完成，且验证结果与原计划预期一致；
- `not_completed`：根据当前真实状态能够验证动作尚未发生或未达到原计划结果；
- `state_uncertain`：无法可靠验证、证据冲突、审计记录缺失，或动作可能只完成了一部分。

不得根据“最后一条日志”直接推定动作成功或失败；不能验证时必须标记 `state_uncertain`。

## 3. 明确禁止

恢复流程不得：

- 从中断点自动续跑；
- 自动补做被判定为未完成的动作；
- 自动重试失败或状态不确定的动作；
- 自动回滚已经完成的动作；
- 复用旧 `plan_hash`、授权 token、确认窗口、有效期或旧 L3 固定短语结果；
- 把旧计划直接恢复为“可执行”；
- 仅凭模型推测、审计记录或缓存状态替代当前真实状态检查。

## 4. 恢复扫描与报告

恢复扫描原则上先使用 L0/L1 受限只读工具。若确认当前状态本身需要产生副作用，则该检查必须退出自动恢复流程，改为向用户说明限制并等待决定。

恢复报告至少包含：

```text
原 task_id / plan_id / plan_version
中断原因和可确认的最后时间点
逐项动作的 completed / not_completed / state_uncertain 分类
当前状态证据摘要
无法验证的原因
已完成动作不会自动回滚的说明
未完成动作不会自动补做的说明
重新规划所需的下一步
```

完整详情使用正式界面或恢复报告展示；语音只按当前人物模板做简短、真实、不淡化风险的摘要。

## 5. 重新规划与授权

只有用户明确选择继续处理后，系统才能基于恢复扫描结果创建新计划或新版本。新计划必须：

1. 重新扫描目标与前提；
2. 重新生成动作清单；
3. 展示相对旧计划的差异；
4. 重新经过 Schema、路径、策略和状态预检；
5. 重新完成对应 L2/L3 授权。

旧计划、旧确认和旧授权均不得迁移到新计划。L3 仍须在新的独立确认状态完整输入或说出“确认执行”。

## 6. 与实时对话及人物模板的关系

恢复过程仍属于持续实时对话的一部分。AI 应先用人物模板简短说明“任务已中断，不能直接继续，需要先检查当前状态”，随后把完整技术细节放入界面。人物表达不得把状态不确定说成已经成功或已经失败，也不得诱导用户快速重新授权。

## 7. 用户主动说“停”或点击停止

“停”按当前上下文处理，但始终优先于普通对话和计划调度：

- 仅在聊天或 TTS 播放时：停止当前回复和播报，清空该回复的待播队列，继续保持实时监听；
- 等待 L2/L3 授权时：取消确认、关闭确认窗口，使当前授权状态和部分确认短语失效；
- 正在执行电脑任务时：立即阻止未开始的后续动作；当前动作可安全取消则请求协作式取消，不可安全中断则等待原子动作返回，但不得开始下一步。

执行任务被停止后，原计划和全部授权失效。系统不自动回滚已完成动作，不自动补做未完成动作；必须重新扫描并按 `completed`、`not_completed`、`state_uncertain` 汇报实际状态。继续处理必须重新规划、预检和授权。

“停”不等于退出持续实时对话，也不等于关闭程序。

## 8. 取消、中止与关闭程序

### 8.1 用户取消

用户取消表示主动放弃当前任务。尚未开始有副作用动作时，直接关闭任务并使计划、确认和授权失效；如果执行已经开始，则先执行“停”的规则，再重新扫描真实状态。任务记录为 `user_cancelled`。取消不关闭程序，持续实时对话保持可用。

### 8.2 系统中止

系统因工具失败、前提变化、目标状态变化、审计失败、安全校验失败或状态无法确认而停止任务时，记录为 `system_aborted`。系统必须阻止后续动作，使原计划和授权失效，不自动重试、跳过、修复或回滚，并重新扫描实际状态。是否重新规划只能由用户决定。

### 8.3 关闭程序

- 无任务执行时：停止回复、TTS 和监听，清理临时音频、待播队列和内存闲聊上下文，然后退出；
- 规划或等待授权时：先按用户取消处理，再清理并退出；
- 任务执行时：进入安全退出状态，阻止后续动作；当前动作可安全取消则请求取消，不可安全中断则等待原子动作返回；重新扫描、记录状态、使旧计划和授权失效后再退出。

正常关闭不得强杀不可安全中断的动作。通过任务管理器、系统关机、断电或其他外部方式强制终止时，按崩溃/重启规则处理，下次启动不得自动续跑。

## 9. DeepSeek/Agent 网络与 API 故障

以下规则统一适用于网络错误、连接断开、限流、首包超时、总响应超时、流式响应中断、空响应、未知事件，以及响应无法通过既定 Schema 或格式校验的情况。

### 9.1 闲聊回复期间

- 立即停止本次回复生成和对应 TTS，丢弃未完成的流式回复；
- 不把不完整回复写入正式对话历史，也不得把它作为后续上下文中的完整事实；
- 不自动重试、不自动切换模型、Agent、CLI 或其他运行通道；
- 助手程序和实时监听保持运行，使用人物模板简短说明本次回复没有完成；
- 只有用户明确要求重试后，才能使用新的 `request_id` 发起新请求。

### 9.2 分析、规划或等待授权期间

- 当前电脑任务记录为 `system_aborted`；
- 未完成、空白、流中断或未通过 Schema 校验的模型输出不得形成执行计划、工具调用或授权请求；
- 当前计划、确认窗口和全部授权失效，不得复用部分生成的计划或先前授权；
- 用户决定继续时，必须使用新的请求重新分析和规划，并重新完成预检、计划展示及 L2/L3 授权。

### 9.3 本地执行期间

冻结且已授权的本地计划原则上不得依赖 Agent 持续在线。只有当全部动作、停止控制、安全校验和结果验证均可由本地执行器按冻结计划独立完成，且不需要模型追加决定或参数时，Agent/API 故障才不改变已经确认的执行语义。

如果故障导致任务控制、停止响应、安全判断、动作参数或结果验证无法继续可靠工作，则必须：

```text
阻止所有尚未开始的动作
→ 安全取消当前动作，或等待不可安全中断的原子动作返回
→ 不开始下一步
→ 使用受限只读工具重新扫描真实状态
→ 任务记录为 system_aborted
→ 原计划和授权失效
```

不得为了继续执行而临时改用不完整流式文本、CLI、Claude Code、Codex、其他模型或新的 Agent 决策。

### 9.4 执行完成但自然语言汇报失败

- 不得把已经通过本地验证的执行结果改记为失败或状态不确定；
- `ResultVerifier`、`result.json` 和审计事件仍是结果事实来源；
- 界面使用本地正式模板展示实际结果，并单独记录“Agent 汇报生成失败”；
- 不得因汇报失败重复执行任何电脑动作；
- 后续如需重新生成自然语言摘要，只能读取既有结构化结果，不得重新触发执行。

### 9.5 统一重试、切换与错误展示规则

- 不自动重试，包括不自动按照服务端 `Retry-After` 等待后重试；限流和建议等待时间只能作为脱敏信息展示给用户；
- 不自动切换 DeepSeekHarness CLI、Claude Code、Codex、其他模型或 Provider；
- 不使用不完整流式文本生成计划、调用工具、补充动作参数或请求授权；
- 用户明确要求重试时必须建立新的 `request_id`；涉及电脑任务时还必须重新分析、规划、预检和授权；
- API key、请求正文、隐私内容、完整响应和内部堆栈不得出现在语音中；本地界面和日志只显示完成脱敏后的错误类别、阶段、时间和诊断标识。

## 10. ASR 整体不可用时的降级（已定稿）

- ASR 整体不可用时自动进入文字输入模式，停止识别并清除当前未完成的识别轮次。
- 残留音频不得提交给未经用户配置的其他 ASR Provider；不自动切换 Windows 语音识别、云端 ASR 或其他服务。
- 文字输入仍通过 DeepSeekHarness Python SDK 调用同一个 Harness Agent；每次提交创建新的 `request_id`。
- Harness 仍只负责理解、规划和汇报；电脑任务必须经过 Schema、PathGuard、PolicyEngine、L2/L3 授权、本地受控执行器和 ResultVerifier。
- L2 继续使用“允许执行”弹窗；L3 先点击“允许执行”，再在独立确认输入框完整键入“确认执行”，并绑定当前计划信息和有效期。
- TTS 可用时采用“文字输入、语音输出”；TTS 也不可用时采用纯文字交互。

详细输入与验收规则见 `../04-asr.md` 和 `../08-text-end-to-end.md`。

## 11. ASR 恢复探测与退出文字模式（已定稿）

- 文字模式允许后台低频检查本地模型、Provider、设备和固定本地测试音频，但不得使用用户正在说的话做后台测试，也不得上传测试音频。
- 必须连续多次检查通过后才标记 ASR 已恢复；检查次数和间隔在真机测试阶段配置。
- 恢复后只提示用户“语音识别已恢复，可以切回语音输入”，不得自动切回。
- 只有用户点击“切回语音”或通过文字明确要求后才能切换，而且必须等待安全空闲点。
- 用户键入、Agent 回复/TTS、方案查看或修改、L2/L3 授权、任务执行及恢复扫描期间均不得切换。
- 切回前清除旧音频与识别事件，创建新的输入会话边界，不复用旧请求、确认或授权，并执行一次仅限本机的麦克风与 ASR 联合测试。
- 联合测试音频不提交 Agent、不进入正式历史，并按临时音频规则删除；测试失败时继续保持文字模式。
- 用户可随时通过设置或状态栏手动触发“重新检测语音识别”。

## 12. TTS 主 Provider 故障衔接（已定稿）

- VoiceStudio 故障只影响语音输出；完整文字、电脑任务、冻结计划、授权状态、执行状态和结构化结果均继续按原规则处理。
- 以完整句子为切换边界：已完整播放的句子不重播；当前句尚未播放且存在用户预先配置的 Edge 音色时，可由 Edge 从当前句开始。
- 当前句已经播放一部分后失败时，不在半句中换声音，也不自动重播整句；停止本轮播报，保留完整文字，并从下一轮回复开始使用已配置的 Edge TTS。
- 未预先配置 Edge 音色时直接进入文字输出；不得临时选择音色或覆盖 VoiceStudio 默认 VoiceProfile。
- Edge TTS 也失败时停止合成并清理残留音频和待播队列；会话继续纯文字交互，不尝试第三个 Provider，不循环重试。
- L2/L3 风险说明、方案、按钮和固定确认要求必须始终以正式界面为事实来源；TTS 故障不得阻塞、代替或自动批准授权，也不得重播已过期授权提示。
- 界面只显示脱敏后的 Provider 状态、错误类别、阶段和诊断标识。VoiceStudio 恢复后仅从下一轮新回复恢复原 VoiceProfile，不重播已经播放或已转为文字的旧内容。

详细规则与验收见 `../02-tts-voicestudio.md`。

## 13. 启动阶段 ASR/TTS 模型加载失败与超时（已定稿）

- ASR 和 TTS 都是可独立降级的语音能力，不是程序启动的全局阻塞条件。程序必须先启动正式界面、文字输入、Harness 接入适配器、本地安全链和审计基础设施。
- ASR 与 TTS 分别使用独立、有上限的启动检查或加载期限；任一组件失败、模型不完整、Provider 初始化失败或超过期限时，只将该组件标记为 `unavailable_startup`，清理未完成加载和临时资源，不无限等待、不循环重启。
- ASR 启动失败：立即进入文字输入模式；TTS 启动失败：保留文字输出，若存在用户预先指定的 Edge 音色则按既定规则为后续新回复兜底，否则使用纯文字。两者同时失败时使用文字输入、文字输出。
- 启动阶段降级不得改变 Agent、电脑任务安全链、计划、授权、执行状态或结构化结果。L2/L3 授权仍以正式界面为准；语音能力失败不能代替、阻塞或批准授权。
- 启动降级后如果组件随后恢复，不得突然打断用户正在输入、查看方案、授权或执行任务；只标记恢复并提示用户。ASR 切回继续遵守用户明确请求、等待安全空闲点和本机联合测试；TTS 只从下一轮新回复恢复，不抢回当前回复。
- 启动阶段不自动恢复上次电脑任务；发现遗留任务按崩溃/重启恢复规则处理，旧计划与授权不得复用。
- 具体启动期限、资源阈值、连续成功次数、冷却和后台健康检查策略在后续“会话预热、运行期故障与 Provider 恢复”专题中定稿；但任何实现都必须保留明确的超时上限。

## 14. 音频组件会话级故障与恢复（已定稿）

### 14.1 总原则：音频通道与任务事实隔离

- ASR、TTS、麦克风、扬声器和 Provider 都是输入输出通道，不是电脑任务事实来源。
- 音频故障不得改变 DeepSeekHarness Agent 边界、Schema、PathGuard、PolicyEngine、L2/L3、本地执行器、ResultVerifier、审计或电脑当前真实状态。
- 音频状态与任务状态必须独立保存；任何界面、状态机或日志都不得用“音频失败”覆盖“任务仍执行”“请求已提交”或“状态不确定”等事实。
- 不完整语音、interim、事件顺序不确定的结果、旧缓冲和恢复探测材料不得进入 Agent、停止控制或授权流程。
- 恢复后必须创建新的 session、utterance、Provider 请求和音频队列边界；不得复用旧请求、旧音频、旧授权或旧待播队列。

### 14.2 ASR 会话预热与运行期故障

- ASR 会话预热独立、可取消且有上限，不阻塞文字输入；界面显示准备状态，并保留文字输入、取消和重新检测入口。
- 预热期间音频不进入正式 Agent 输入，也不在加载完成后补识别。成功后清理预热材料和旧事件，再创建新的 `session_id`/`utterance_id`。
- 预热失败、超时或取消后进入文字输入，不创建 Agent 请求、计划或授权；手动重试必须创建全新且有上限的尝试。
- 运行期故障只结束当前语音输入轮次。当前 utterance、interim、临时音频和旧事件一律清理；最终文本与故障顺序不确定时不提交。
- 只有最终事件可靠归属于当前 utterance、顺序明确、未重复且尚未创建请求时，才可提交一次。已经创建 `request_id` 后不得撤回、重发或创建第二个请求。
- 半句停止、取消、允许或确认均不生效；L3 语音确认中故障时当前确认轮次立即失效。
- ASR 故障本身不暂停、取消、回滚、重试或重启电脑任务；系统自动进入文字输入模式。

### 14.3 TTS 会话预热与运行期故障

- Agent 文字回复不等待 TTS，必须立即显示。TTS 并行预热且有明确上限。
- 当前回复尚未播放且预热及时成功时，可从第一句播报；超时或失败后当前回复保持文字，不在恢复后自动补播。
- 已配置 Edge 时只能按完整句边界兜底；没有配置则纯文字。手动重新准备必须创建新的 TTS session，清理旧请求与队列，不重播旧回复。
- 当前句尚未实际播放时，可以切到用户预先指定的 Edge 音色；已经播放任意部分时，不半句换声、不整句重播，停止本轮语音，剩余旧句子不跨 Provider 续播。
- 已完整播放或已转文字的内容不重播。VoiceStudio 和 Edge 均失败时清理残留并转纯文字；不尝试第三 Provider、不循环切换、不修改默认 VoiceProfile。

### 14.4 授权与任务隔离

- L2/L3 正式界面是授权事实来源，语音只作辅助。ASR/TTS 故障不得自动批准、拒绝或延长授权。
- L3 始终绑定当前 `plan_id`、版本、哈希、动作和有效期；旧语音提示、旧识别结果和旧确认状态不能复用。
- 任务执行中普通音频故障不自动暂停、取消、回滚、重试或开始下一步。只有可靠的用户输入可以触发停止；文字“停”和正式停止按钮继续遵守既定规则。

### 14.5 冷却、健康探测与重新启用

统一建议状态流：

```text
FAILED
→ COOLDOWN
→ PROBING
→ 连续健康检查通过
→ RECOVERED_PENDING_USER / RECOVERED_PENDING_NEXT_REPLY
→ 安全边界
→ 正式启用
```

- 探测与正式启用分离；Provider 故障后进入冷却，不为每次请求反复初始化或循环重试。
- ASR 只使用本机固定测试音频、模型/Provider/设备检查；不得使用用户真实话语、任务、路径或授权内容。
- TTS 只使用固定无隐私测试文本；测试结果不进入历史或正式播报。
- 连续检查次数、间隔、冷却期、最大尝试次数、联合测试时限、模型保温和当前回复等待窗口留到真机测试，但都必须有上限。
- ASR 恢复后只提示并等待用户明确切回；不自动开麦、不抢占文字输入、不恢复旧 utterance/request。
- TTS 恢复后只从下一轮新回复生效；不补播当前或旧回复。
- 手动检测每次都是新的、有上限的尝试；恢复不得修改默认 ASR Provider、VoiceProfile、Edge 配置或安全策略。

## 15. GitHub 对比优化后的实现约束

以下内容是 2026-09-19 固定版本源码对比后的工程约束，不改变前文已经定稿的行为边界：

- 重试分为传输层、Agent 请求层和电脑副作用动作层。前两层只能在未创建新副作用事实时有上限地处理；副作用动作默认不得自动重试。
- `state_uncertain` 是独立终态/恢复分支，不能自动改写为成功、失败、可重试或可回滚；必须重新扫描真实状态。
- 动作账本至少记录 `execution_id`、`action_id`、`attempt_id`、`executor_instance_id`、`fencing_token`、`started_at`、`finished_at`、取消请求时间、返回状态和验证状态。
- heartbeat、checkpoint、worker attempt 或 Provider 健康状态只提供运行线索，不能替代电脑真实状态、ResultVerifier 或重新授权。
- 审计事件至少包含唯一事件 ID、单源序号、前后状态、来源实例、`previous_event_hash`、`event_hash` 和防重复写入语义。
- ASR/TTS 恢复必须校验 session、generation、sequence；旧 generation、迟到、重复和跨 session 事件只进入诊断/审计。

完整证据与新增验收测试见 [`../research/github-comparison-and-optimization.md`](../research/github-comparison-and-optimization.md)。

## 16. 后续真机参数与禁止改变事项

- I.9 的行为边界已经定稿；固定版本 GitHub 对比只补充工程契约，后续只允许通过真机测试优化实现参数，不得改变上述安全原则。
- ASR/TTS 预热超时、冷却时间、探测间隔与最大次数、连续成功次数、联合测试时限、模型保温时间和当前回复等待窗口暂不写死。
- 所有参数无论最终取值如何，都不得造成无限等待、无限重试、循环 Provider 切换、旧内容补播或绕过安全链。
- 固定版本 GitHub 源码对比和 P0-P11 路线图已经完成；当前仅做规划一致性收口。未来实现必须从 P0/P1 开始，不得按主题编号直接从 ASR/TTS 开工。
