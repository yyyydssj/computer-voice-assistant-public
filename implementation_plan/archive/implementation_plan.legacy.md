## 1. 项目概览

- **目标**：做一个能实时语音对话、并能听懂指令后操作电脑的 AI 助手（全语音闭环）。
- **技术栈**：Python + sounddevice / openWakeWord / 声纹模型 / silero-vad / sherpa-onnx(SenseVoice) / DeepSeekHarness Python SDK（运行时主 Agent） / VoiceStudio 本地 TTS（主 Provider，支持 preset、提示词设定和音频克隆音色） / Edge TTS（可配置兜底） / asyncio。
- **架构原则**：前后端分离——决策/执行/安全核心与语音前端解耦，未来手机接入只需换前端（本次不实现）。
- **目录结构**：见 `../design.md` 第十一节；其中 `models/`、`logs/`、`plans/` 和 `memory.md` 的实际内容按 `[本地运行数据]` 或 `[敏感信息]` 处理。

### 1.2 运行时主 Agent 与接入方式（项目级决策）

本项目运行时确定采用 **DeepSeekHarness** 作为电脑语音助手的唯一默认主 Agent，负责闲聊、工作模式下的任务理解、信息分析、方案生成、错误解释和结果汇报。本文规则仅在使用本电脑语音助手时生效，不延伸为其他场景下使用电脑或其他软件的通用规则。

接入方式按以下优先级确定：

1. **正式运行时通道：DeepSeekHarness Python SDK**。电脑语音助手以 Python 主程序调用 SDK，管理会话、`session_id`、超时、事件和错误；使用受限 profile/插件。
2. **诊断、测试和故障恢复通道：命令行进程**。仅用于手动验证、诊断或用户明确要求的恢复操作，不作为正常运行时主通道。
3. **后续扩展通道：本地服务/API**。暂不作为 MVP 核心；待持续运行、多客户端或前后端分离需求明确后再设计。

启动与会话生命周期确定如下：

- 程序启动时只初始化 SDK 适配器并检查本地配置，不创建 DeepSeekHarness 会话，也不发起模型请求。
- 第一次收到实际闲聊或工作请求时，才延迟创建对应会话；没有用户请求时不得为了“预热”自行发送内容。
- 闲聊会话与工作会话完全分开。闲聊上下文只保留在当前进程内存中，连续闲置满 **30 分钟**后销毁，默认不落盘。
- 每项工作任务建立独立工作会话并绑定 `task_id`；任务完成、用户取消或任务失败后关闭该工作会话，不得把其计划、授权状态或工具结果直接沿用到下一项任务。
- 从闲聊切换到工作模式时，不自动传递完整闲聊历史；只传递用户本次明确提出的任务、用户明确引用的内容以及完成该任务确实必要的最小上下文。
- 每次 Agent 请求生成唯一 `request_id`。工作请求同时关联 `session_id` 和 `task_id`；形成计划后再关联 `plan_id` 与 `plan_version`，尚未形成计划时后两项为空，不得伪造占位计划。
- SDK 超时、崩溃、断线或返回格式错误时，立即停止当前流程，不自动重试、不自动改用 CLI、不自动切换 Claude Code/Codex；当前任务中已经存在的计划和授权全部失效。系统必须显示具体错误原因和可选解决方案，等待用户决定是否重新分析。

运行时职责分层：

```text
DeepSeekHarness = 理解、规划、解释、汇报
本地安全层 = SchemaValidator + ToolRegistry + PathGuard + PolicyEngine + ConfirmationManager
本地受控执行器 = 只执行冻结且获授权的 plan.json
ResultVerifier = 检查实际结果并生成结构化事实
```

硬边界：

- DeepSeekHarness 输出必须视为不可信输入，不能直接执行自然语言命令、脚本、路径或参数。
- 不向 DeepSeekHarness 开放默认 Shell、PowerShell、Python、批处理、任意脚本、管理员权限或任意鼠标键盘控制。
- 实际电脑修改只能由本地受控执行器按照通过校验、预检、用户授权和执行前重新校验的冻结计划完成。
- DeepSeekHarness 失败时不自动切换 Claude Code、Codex 或其他 Agent；必须停止当前任务、记录错误、使旧计划和授权失效，并等待用户决定是否重新分析。
- 用户明确选择其他 Agent 时，视为新的分析流程，必须重新扫描、重新制定计划、重新预检和重新授权。
- Agent 适配层保留可替换接口，但更换 Agent 不能改变本地安全层和项目级授权规则。

### 阶段 9：语音闭环（录音→ASR→LLM→工具→TTS）
- 目标：拼出"说话 → 回复语音"。
- 步骤：
  - [ ] 串起：录音 → ASR（默认 SenseVoice，可选 VoiceStudio 流式 Provider）→ LLM(工具) → TTS（默认 VoiceStudio，可选 Edge TTS 兜底）
  - [ ] 先用按键触发代替唤醒词（按一下开始录音），跑通闭环

- 产出：可用的语音对话原型
- 验收：按住触发 → 说话 → 听到小饼语音回复，能指挥电脑

### 阶段 10：唤醒词 + 声纹
- 目标：后台常驻，喊「小饼」才响应，且只认主人声音。
- 步骤：
  - [ ] `wake/` 集成 openWakeWord，持续监听
  - [ ] 检测到「小饼」后，用声纹模型比对主人声纹模板

- 验收：喊「小饼」能唤醒；别人喊或你之外的声音不唤醒

### 阶段 11：VAD 判断说完 + 状态机主控循环
- 目标：说完自动停、自动走完流程、回到待机。
- 步骤：
  - [ ] `audio/` 加 VAD：唤醒后录音，连续静音约 1 秒判说完

  - [ ] 一轮结束后自动回待机
- 产出：完整主控循环
- 验收：唤醒后不用按键，自然说话→自动识别→回复→回待机

### 阶段 12：打断 barge-in + 回声消除/降噪
- 目标：AI 说话时你能插话打断；AI 自己的声音不误触发。
- 步骤：
  - [ ] 播报/思考时仍监听人声，检测到说话立即停 TTS、进录音

- 产出：打断 + 预处理
- 验收：能插话打断；AI 自己播报不会误唤醒自己

### 阶段 13：真机调优
- 目标：调出好手感。

### 7.2 对话模式与用户决策边界（硬规则）

系统在语义上区分闲聊模式与工作模式；两种模式的称呼、视觉表现和切换方式可以后续配置，但不得改变下列安全边界。

**闲聊模式**：

```text
可以自然聊天、讨论思路、解释知识、给出建议和陪伴性回应。
闲聊内容不自动进入执行计划，不调用修改类工具，不产生任何授权。
闲聊中的“好、嗯、可以、行、帮我处理”等自然回应，不能被推定为文件操作授权。
```

**工作模式**：

```text
助手是受约束的工具：理解需求、查询必要信息、复述目标、指出风险、提供多个解决方案、生成候选计划、执行前预检、执行后验证和汇报。
助手只能在用户明确选择方案、确认具体计划并完成对应 L2/L3 授权后，按已确认计划调用受限工具。
建议、诊断、错误解决思路和“重新制定计划”的提示永远不等于执行指令或授权。
```

用户负责：

```text
目标、范围、规则、执行顺序和冲突策略
在候选解决方案中作出选择
排除项、重新规划与最终授权
是否保存为 Skill
是否修改已有 Skill
```

AI 负责：

```text
理解自然语言
复述执行清单
指出歧义和风险
提出建议与可选解决方案
生成具体动作和候选计划
按用户已确认计划调用工具
执行前预检、执行后验证并汇报
```

AI 不得：

```text
擅自扩大范围
自行判断“没用”并删除
改变用户已确定的规则
将建议、错误解决方案或计划草稿自动变为执行
自动关闭占用程序、修改权限、提权、清理磁盘、改写目标路径、跳过失败项或自动重试
绕过系统黑名单或授权校验
自动保存或修改 Skill
将闲聊中的“好、嗯、可以、行”当作授权
```

### 7.3 安全等级与系统黑名单

系统文件黑名单是硬拒绝规则，即使用户明确允许也不能绕过。黑名单及其子路径至少包括：

```text
C:\Windows\
C:\Program Files\
C:\Program Files (x86)\
C:\ProgramData\
C:\Recovery\
C:\System Volume Information\
C:\$Recycle.Bin\
C:\Users\<当前用户>\AppData\
C:\Users\<当前用户>\NTUSER.DAT
C:\bootmgr
C:\pagefile.sys
C:\hiberfil.sys
C:\swapfile.sys
```

下列系统级操作永久禁止：

```text
注册表、服务、计划任务、驱动、Windows Defender、防火墙
系统环境变量、启动项、磁盘格式化/分区、系统恢复配置
管理员权限提权
```

路径检查不能依赖字符串包含判断。必须规范化绝对路径，处理 `..`、环境变量、大小写、斜杠、UNC、映射盘、符号链接、Junction 和 Reparse Point，并在执行前再次检查真实目标路径。

MVP 路径边界：

```text
允许访问根目录：<STUDY_ROOT>
默认工作目录：<STUDY_ROOT>\AI工作区
```

- 文件工具允许访问 `<STUDY_ROOT>` 及其子目录，不因目标位于 `AI工作区` 之外而额外禁止。
- `<STUDY_ROOT>\AI工作区` 只是相对路径和未明确目录时的默认落点，不是唯一可操作目录。
- 允许访问边界不等于执行授权：任何写入、复制、移动、重命名或移入回收站的操作，都必须先生成具体执行方案并经用户确认。
- 执行方案必须列出完整规范化路径、操作类型、文件数量、排除项、执行顺序、冲突处理、风险和预期结果。
- 方案确认后，路径、文件数量、内容哈希、目标或参数发生变化时，旧确认立即失效，必须重新扫描、生成方案并确认。
- `<STUDY_ROOT>` 之外的路径、其他盘符、UNC/网络路径和未能可靠解析的路径，不属于 MVP 文件工具访问范围。

| 等级 | 示例 | 默认行为 |
|---|---|---|
| L0 | 时间、版本、普通状态查询 | 直接执行 |
| L1 | 列目录、读普通文本、搜索、查询进程 | 受限直接执行 |
| L2 | 创建、写入、复制、移动、重命名、整理 | 居中模态权限弹窗；点击“允许执行”后继续校验和执行 |
| L3 | 删除、覆盖、终止进程、受控命令 | 居中模态权限弹窗 + 第二重输入固定确认短语“确认执行”；严格限制 |
| L4 | 系统目录、注册表、服务、驱动、管理员操作 | 永久禁止，不提供授权按钮 |

### 7.4 双重确认、权限弹窗与语音播报

普通文件改动包括创建、写入、追加、覆盖、复制、移动、重命名、删除和移入回收站。所有需要授权的操作统一遵守以下规则：

- 权限确认采用**居中模态弹窗**；弹窗未处理前，不继续执行对应任务。
- 权限按钮固定使用“允许执行”和“拒绝”，不使用“确定”和“取消”。
- 权限弹窗出现时，使用人物模板进行简短语音提醒；语音只提醒用户查看弹窗，不代替弹窗授权。
- 用户点击弹窗中的任意按钮后，立即停止当前语音播报，不等待当前句子播报完毕。
- 点击“允许执行”后，仍须重新校验计划、路径、数量、哈希、参数和目标状态；校验失败时拒绝执行。
- 关闭弹窗、按 Esc、点击“拒绝”或弹窗超时均不产生授权；弹窗超时不得自动执行。

L2 普通修改操作采用：

```text
生成执行方案
→ 用户确认方案
→ 居中模态弹窗展示正式执行摘要
→ 用户点击“允许执行”
→ 重新校验
→ 执行并验证
```

L3 高风险操作采用：

```text
居中模态弹窗展示风险与完整方案
→ 用户点击“允许执行”进入第二重确认
→ 用户在独立确认状态输入或说出完整固定短语“确认执行”
→ 系统检查当前确认窗口、plan_hash、版本和有效期
→ 重新校验
→ 执行并验证
```

L3 的用户可见确认短语固定为：

```text
确认执行
```

这里的“动态”体现在确认窗口、`session_id`、`plan_id`、`plan_version`、`plan_hash`、`operation_id` 和过期时间的动态绑定，而不是每次让用户记忆复杂随机数字。短语必须完整匹配，不接受同义词、缩写、追加语气词或模糊识别结果。

确认只在独立确认状态解析。普通聊天中的“好、嗯、可以、行、对、没问题”永远不产生授权。

确认必须绑定：

```text
session_id
plan_id
plan_version
plan_hash
operation_id
规范化路径
源文件哈希
写入内容哈希
确认阶段
授权方式
confirmation_phrase（L3 固定为“确认执行”）
confirmation_window_id
创建时间和过期时间
```

用户提出新任务、取消/停止、编辑文档、文件哈希变化、参数变化、计划过期、弹窗被关闭或播报被打断时，确认立即失效，并从第一阶段重新开始。

任务结果采用右下角非模态通知，默认停留 3 秒，用户可以手动关闭；全部成功、部分成功、失败、严重失败和系统拒绝必须使用正式、明确的状态说明。结果通知同时进行人物模板语音播报，语音只播报简短摘要，完整详情保留在通知详情和执行文档中。严重失败和系统拒绝同样默认停留 3 秒。

### 7.5 用户负责规划，AI 只复述和校验

遇到“整理一下”“弄好一点”“清理没用的”等模糊表达：

1. 先判断是闲聊、咨询还是授权操作；
2. 低风险只读操作可以主动执行；
3. AI 可以主动给出 1~2 个建议方案；
4. 不得自行删除、改名、覆盖或大范围移动；
5. 用户确定规则后再生成具体动作计划；
6. “没用”不能由 AI 自行判断并删除。

推荐对话方式：

```text
我先帮你看看，不会动文件。
我建议按文件类型整理，只移动、不改名、不删除。要按这个方案吗？
我把具体动作写进执行文档了，请学长检查。
```

### 7.6 双层执行文档

复杂或有文件改动的任务建立：

```text
plans/<plan-id>/
├─ execution_plan.md
├─ plan.json
└─ result.json
```

- `execution_plan.md`：用户阅读、检查、语音修改和手动编辑；
- `plan.json`：程序校验、确认和执行的唯一依据；
- `result.json`：记录每个动作的成功、失败、跳过、验证和错误。

生成复杂方案后打开 Markdown，语音只做自然提醒：

> 执行文档我写好了，请学长检查。

打开、查看或编辑文档都不等于授权。

Markdown 可编辑：

```text
目标、范围、排除项、文件规则、递归设置、冲突处理
具体动作表中的增加、删除、修改和跳过
```

Markdown 不可用于改变：

```text
系统黑名单、永久删除禁用、管理员权限禁用、分级授权与 L3 第二重确认要求
路径安全检查、确认状态、计划 ID、计划哈希和执行结果
```

Markdown 不允许嵌入任意 PowerShell、Python、Shell、批处理或外部脚本。任何文档保存都生成新版本并使旧确认失效；程序必须等待保存稳定、重新解析、重新扫描和重新校验后才能重新确认。

### 7.7 执行链路

```text
用户计划
→ AI 复述执行清单
→ 本地生成具体动作
→ ToolRegistry
→ Schema 校验
→ PathGuard
→ PolicyEngine
→ 生成并打开执行文档
→ 用户语音修改或直接编辑
→ 重新解析和校验 plan.json
→ 第一次确认
→ 执行前重算路径和文件哈希
→ 备份
→ 第二次确认
→ 执行
→ ResultVerifier 验证
→ 写入 result.json 和文档
→ 自然语言汇报
```

每个工具必须声明名称、输入/输出 Schema、风险级别、是否需要确认、超时、输出大小、允许路径、幂等性、预览方式和撤销策略。

第一版只开放结构化工具，不让模型直接执行任意 PowerShell。删除默认移入回收站；永久删除禁用。修改、覆盖、重命名和移动应尽量保存备份并记录撤销信息。

### 7.8 音频实现预留

MVP-1 先按键触发，但音频层从一开始按流式帧设计：

```text
AudioFrame
→ 输入队列
→ pre-roll 环形缓冲
→ VAD
→ 录音缓冲
```

### 12.2 待定稿问题明细

#### A. MVP 工具清单与权限等级（已定稿）

本项已于 2026 年 9 月 13 日确认。MVP 只开放结构化工具；工具权限由 `ToolRegistry`、Schema 校验、`PathGuard` 和 `PolicyEngine` 强制执行，不能由大模型、Skill、执行文档或普通配置自行提升。

##### A.1 权限等级定义

| 等级 | 含义 | 默认行为 |
|---|---|---|
| **L0** | 低风险、只读且范围天然有限 | 可直接执行，但仍须参数校验 |
| **L1** | 只读，但可能暴露较多系统或隐私信息 | 可直接执行，必须受路径、数量、内容和超时限制 |
| **L2** | 有副作用，但通常可恢复或影响范围较小 | 方案确认后点击“允许执行”，再重新校验 |
| **L3** | 破坏性、批量性或影响范围较大的操作 | 点击“允许执行”后，必须输入或说出当前计划绑定的固定短语“确认执行” |
| **L4** | 难以可靠约束、容易绕过安全边界或需要系统级权限的操作 | MVP 默认拒绝；即使用户口头允许也不能执行 |

统一确认规则：

- L0/L1 只读工具可以直接执行，但不能绕过路径守卫、参数校验、结果数量限制和敏感字段过滤。
- L2 工具在用户查看方案后，通过“允许执行”完成授权；授权后仍须重新校验。
- L3 工具使用风险说明→点击“允许执行”→输入或说出固定短语“确认执行”第二次确认；第二次确认必须绑定当前计划上下文并重新校验。
- L4 工具在 MVP 中不注册为可执行工具；模型不得输出任意脚本、命令文本或权限提升请求。
- 批量操作必须先展开为完整、可审阅的动作清单，再进行确认；不能用一次模糊确认覆盖未知数量或动态新增的动作。
- 系统文件黑名单是硬拒绝规则，不因用户确认、Skill、文档编辑或模型判断而放宽。

##### A.5 计划级执行语义

同一计划可以包含多个已注册工具调用，但必须遵守：

1. 先生成完整动作清单，并展开每个文件的规范化路径、操作类型和风险等级；
2. 逐项执行 Schema 校验、路径检查、黑名单检查和策略判定；
3. 对批量操作显示完整清单、项目数量和冲突策略；
4. 根据清单最高风险动作执行对应的确认流程；
5. 每项动作独立记录成功、失败、未开始或状态不确定，以及验证结果和错误原因；MVP 不允许跳过失败项后继续；
6. 任一动作在执行中失败、前提变化或状态无法确认时，立即停止整个计划，当前计划和剩余动作的授权均失效；
7. 计划执行期间不得动态增加未确认动作；任何新增或参数变化都必须使旧确认失效并重新确认。

- 每个工具注册项必须声明输入/输出 Schema、风险等级、确认要求、超时、输出大小、允许路径、幂等性、预览方式和撤销策略。

#### B. 路径范围与安全策略（核心原则已定稿）

本项核心原则已于 2026 年 9 月 13 日确认。MVP 文件工具的允许访问根目录为 `<STUDY_ROOT>`；`<STUDY_ROOT>\AI工作区` 继续作为默认工作目录。核心原则已定稿，具体规范化、链接和边界测试在实现阶段按本节硬性约束落实。

##### B.1 允许范围与默认目录

- 允许访问 `<STUDY_ROOT>` 及其所有普通子目录，包括但不限于 `<PROJECT_ROOT>`、`<STUDY_ROOT>\agents`、`<STUDY_ROOT>\codex` 和 `<STUDY_ROOT>\python`。
- 允许访问根目录扩大到 `<STUDY_ROOT>` 后，不额外限制只能操作 `<STUDY_ROOT>\AI工作区`。
- `<STUDY_ROOT>\AI工作区` 仅是默认工作目录：用户未明确指定相对路径基准时，优先以此目录解析；用户明确指定其他 `<STUDY_ROOT>` 子目录时，以用户指定目录为准。
- 不得因为“学习目录”范围较大，就主动扫描、修改或整理未被用户任务包含的其他子目录。
- 访问范围不是授权：所有会产生文件变化的操作，必须先生成具体执行方案并经用户确认，再进入对应 L2/L3 确认流程。

##### B.2 方案确认是所有修改操作的前置门槛

对于创建、写入、复制、移动、重命名和移入回收站，执行链路必须是：

```text
用户提出目标
→ 扫描并明确范围
→ 生成具体执行方案
→ 用户确认方案
→ 重新扫描并校验路径/数量/哈希/参数
→ 按 L2/L3 授权规则执行确认
→ 执行
→ 验证并汇报
```

执行方案至少包含：

- 完整源路径和目标路径；
- 操作类型及逐项动作；
- 文件/目录数量和总大小；
- 明确排除项；
- 执行顺序和依赖关系；
- 同名或目标冲突处理方式；
- 风险、备份和验证方式；
- 预计成功、失败、中止和状态不确定行为；MVP 不支持跳过失败项后继续。

以下情况会使方案和已有确认立即失效：

- 用户扩大、缩小或改变范围；
- 文件数量、路径、内容哈希或目标发生变化；
- 用户编辑执行文档或计划版本变化；
- 操作参数、冲突策略或执行顺序变化；
- 重新启动后恢复未完成计划。

##### B.3 路径规范化与越界防护

- 工具内部统一使用规范化绝对路径；不能用字符串包含判断代替路径关系判断。
- 相对路径必须绑定明确基准；未明确基准时使用 `<STUDY_ROOT>\AI工作区`，不得相对当前进程目录或任意模型工作目录解析。
- 处理并拒绝通过 `..`、重复斜杠、大小写变体、环境变量展开、Windows 短文件名或等价路径绕过根目录限制的请求。
- 最终规范化路径必须位于 `<STUDY_ROOT>` 内；规范化失败、存在歧义或无法确定真实目标时采用拒绝策略。
- 不允许通过盘符切换、映射盘别名、UNC 路径或网络共享绕过 `<STUDY_ROOT>` 边界。
- 执行前必须再次解析实际目标路径；检查通过后若目标路径发生变化，立即终止该动作。

##### B.4 符号链接、Junction 与 Reparse Point

- MVP 默认不把符号链接、Junction、Reparse Point 作为文件操作目标。
- 目录遍历遇到上述对象时，默认不跟随、不跨越，记录为跳过或安全拒绝。
- 源路径或目标路径涉及链接/junction/reparse point 时，不得仅凭表面路径位于 `<STUDY_ROOT>` 内就放行。
- 无法确认真实目标、目标解析失败或解析结果位于 `<STUDY_ROOT>` 外时，必须拒绝。

##### B.5 系统目录、其他盘符和敏感边界

- `<STUDY_ROOT>` 是 MVP 文件工具的唯一允许根目录；`C:\Windows`、`Program Files`、`AppData` 等系统黑名单及其子路径即使通过路径变体出现，也必须拒绝。
- 其他盘符、移动盘、网络盘、UNC 路径和映射盘不进入 MVP 文件工具访问范围；后续若要开放，必须单独讨论并增加安全评测。
- `get_system_info` 和 `get_processes` 的预定义查询不等于获得任意系统文件访问权限。
- 黑名单匹配失败、权限状态不明确、路径状态不明确或安全检查异常时，一律拒绝，不降级放行。

##### B.6 本项定稿后的实施约束

- `PathGuard` 必须同时校验允许根目录、规范化路径、真实目标路径、黑名单、链接类型和执行时状态。
- 所有修改类工具在进入确认前必须绑定已生成的具体执行方案；不能只凭自然语言目标或单个目录名直接执行。
- 只读工具同样不能访问 `<STUDY_ROOT>` 之外的路径；只读不代表可以绕过根目录、链接和敏感字段检查。
- 后续测试必须覆盖路径穿越、环境变量、短文件名、大小写/斜杠变体、UNC、映射盘、链接/junction/reparse point、目标竞态和无法解析时拒绝。

#### C. 文件操作语义与冲突处理（核心原则已定稿）

本项核心原则于 2026 年 9 月 15 日确认：**执行前必须在可验证范围内排除已知错误；执行中任一项失败、前提变化或状态不确定时，立即终止并作废当前计划。助手不得原地重试、跳过失败项后继续，或自行实施“解决方案”。用户处理外部问题后，只能重新扫描、制定新计划并重新授权。**

##### C.1 执行前预检与冲突处理

- 同名目标、来源/目标不存在、路径或链接状态异常、权限不足、空间不足、文件版本/哈希变化等问题，必须在生成可执行计划前检查；预检发现问题时不得开始任何动作。
- 预检失败页面必须给出：错误类型、受影响路径/项目、检测依据、影响范围、不会执行的明确说明，以及不自动执行的解决建议。
- 解决建议可以包括“关闭可能占用文件的应用程序”“由用户自行调整权限”“手动释放空间”“选择其他允许目录”“重新扫描并制定计划”；建议本身不执行任何系统或文件改动。
- 同名冲突、覆盖、改名、移动目标和批量范围必须在候选计划中逐项或按明确分组展示，不能留给执行时临机决定。默认拒绝覆盖，不自动改名。
- 覆盖始终属于 L3：在计划中单独列出、显示受影响文件版本，并经过点击“允许执行”及第二重“确认执行”确认。
- 重命名若改变扩展名、批量“整理”包含的动作或范围发生变化，视为新计划；仍受单次批量上限和相应风险等级限制。

##### C.2 执行中异常、中止与重新规划

- 文件在执行期间被占用、权限临时失效、来源或目标消失、可用空间不足、文件状态变化、校验失败或动作结果无法可靠确认时，立即停止新的动作调度，并终止整个计划。
- 当前计划状态应记录为 `failed`、`aborted_by_user` 或 `state_uncertain`；每项动作记录为 `succeeded`、`failed`、`not_started` 或 `state_uncertain`。已完成操作不因计划终止而自动回滚。
- 失败后当前计划及其剩余动作的授权永久失效；不得提供“重试此项”“跳过此项并继续”“继续执行”或后台自动续跑。
- 失败弹窗使用正式、准确、可审计的表达，至少展示：失败原因、受影响动作与完整/可展开路径、已完成/未开始/状态不确定数量、计划编号、当前计划已终止的状态，以及用户可自行采取的解决建议。
- 失败弹窗只提供“查看执行详情”“重新扫描并制定新计划”和“关闭”。“重新扫描并制定新计划”只启动新的只读分析流程，不自动执行任何操作；新计划必须重新预检、展示差异并重新完成授权。
- 用户说“停”、点击终止或关闭执行流程时，同样停止尚未开始的动作；不承诺回滚已完成动作，当前正在进行的动作必要时标记为 `state_uncertain`。

##### C.3 异常类型的标准建议

| 异常类型 | 标准说明 | 可以给出的解决建议 | 助手禁止的行为 |
|---|---|---|---|
| 文件被占用 | 文件正被其他程序使用，当前计划已终止 | 由用户关闭相关程序后重新扫描 | 自动关闭程序或强制解除占用 |
| 权限不足 | 当前目标位置不可写，当前计划已终止 | 由用户选择可写目录或自行调整系统权限后重新扫描 | 修改 ACL、提权或请求管理员权限 |
| 来源/目标消失或变化 | 文件系统状态已偏离计划快照，当前计划已失效 | 恢复设备/路径或检查实际文件后重新扫描 | 猜测替代路径或沿用旧计划 |
| 磁盘空间不足 | 目标卷空间不足，当前计划已终止 | 由用户手动释放空间或选择合规的新目标后重新扫描 | 自动清理文件、回收站或改写目标 |

##### C.4 本项定稿后的实施约束

- 计划生成器必须在授权前完成来源、目标、权限、冲突、文件版本/哈希、目标空间和路径安全预检，并将预检结果绑定至计划哈希。
- 执行器在每项动作开始前再次校验相关前提；任一失败必须原子地停止后续调度并使计划失效。
- UI 与语音不得把错误建议表述为已执行的修复；语音只提醒用户查看正式失败详情，不能代替重新规划或授权。
- 测试必须覆盖文件占用、权限不足、来源/目标消失、磁盘空间不足、文件变化、用户中止和状态不确定；断言失败后无后续动作执行、无自动修复、无原地重试、无跳过继续。
- 删除一律进入回收站，永久删除保持禁用；计划级回滚的范围和备份策略留待“备份、撤销与验证”主题单独定稿。

#### D. 执行文档和 ActionPlan 数据格式（用户层与 AI 诊断层已定稿）

本项的职责分层于 2026 年 9 月 15 日确认：用户主要查看人可读的 `execution_plan.md`、`result.md`、弹窗和语音摘要；AI 与执行器使用 `plan.json`、`result.json`、按日 JSONL 审计和 SQLite 索引进行精确校验、检索与诊断。用户不需要直接维护 YAML、JSON 或审计日志。

##### D.1 文件职责

- `working/execution_plan.md`：用户可阅读、检查和在受限范围内编辑的工作草稿；它不是执行指令，保存或打开文档永远不等于授权。
- `versions/vNNN/execution_plan.md`：对应冻结版本的人可读执行方案，展示系统最终理解的目标、范围、排除项、动作、顺序、冲突策略、风险、预检摘要和确认要求。
- `versions/vNNN/plan.json`：系统根据草稿解析、路径校验、文件扫描和预检后生成的冻结结构化计划，是执行器唯一允许读取的执行依据；用户、模型和外部文本不能直接改写后执行。
- `versions/vNNN/result.md`：用户主要查看的执行完成总结或错误说明，使用正式、清晰、非技术化的表达；包含总体状态、摘要、已完成/未开始/状态不确定数量、错误原因、验证结果和用户可自行选择的后续方案。
- `versions/vNNN/result.json`：系统生成的详细执行事实，供 AI 和诊断工具判断每项动作的状态、时间、错误码、验证、状态不确定和重新规划关联；用户可以查看但不能编辑历史事实。
- `audit/YYYY/MM/YYYY-MM-DD.jsonl` 与 `indexes/audit_index.sqlite`：主要供 AI 快速按计划、版本、动作、错误码、状态和时间检索；JSONL 是可人工查看的事实来源，SQLite 是可重建索引，不替代用户层总结。

##### D.2 用户可见方案与结果内容

`execution_plan.md` 固定使用以下章节，优先保证用户能快速判断“要做什么、不会做什么和有什么风险”：

```text
1. 计划说明
2. 用户目标
3. 执行范围
4. 明确排除项
5. 具体动作
6. 执行顺序与依赖
7. 冲突处理策略
8. 风险与预检要求
9. 预期结果
10. 用户修改记录
11. 系统校验摘要
```

`result.md` 固定使用以下信息：

```text
1. 总体状态
2. 执行摘要
3. 已完成动作
4. 未开始动作
5. 失败动作与错误原因
6. 状态不确定动作
7. 验证结果
8. 用户可自行采取的解决方案
9. 当前计划是否已终止/失效
10. 关联的重新规划入口或新计划编号
```

- 大批量操作的完整路径清单可以放在 Markdown 附录或可展开详情中；主摘要必须保留范围、数量、总大小、排除项和冲突策略。
- 错误弹窗与 `result.md` 使用同一错误码、计划编号和结果状态，但弹窗只展示必要摘要；完整逐项事实由 `result.json` 和审计日志保存。
- 语音只播报用户层摘要，不播报完整日志、长路径清单、哈希链或内部堆栈；语音不能代替文档、弹窗、重新规划或授权。

##### D.3 系统结构化字段与状态

`plan.json` 每条动作必须具有唯一且稳定的：

```text
operation_id
sequence
dependencies
tool_name
operation_type
source_path / target_path
expected_source_state
expected_target_state
expected_hash / expected_size
conflict_policy
risk_level
preconditions
expected_result
```

计划级字段至少包括：

```text
schema_version
plan_id
plan_version
plan_hash
source_markdown_hash
created_at
expires_at
normalized_scope
exclusions
preflight_snapshot
validation_result
confirmation_binding
status
```

`result.json` 的动作状态只允许使用：

```text
succeeded
failed
not_started
state_uncertain
```

计划状态至少允许使用：

```text
draft
preflight_failed
awaiting_confirmation
authorized

failed

invalidated

```

MVP 不使用 `skipped` 作为执行中失败后的继续语义；如果某动作从未开始，记录为 `not_started`，不能伪装成用户主动跳过。

##### D.4 编辑、解析与哈希规则

- 用户可以编辑 `working/execution_plan.md` 中的目标、范围、排除项、动作、顺序、冲突策略和备注；系统生成的编号、规范化路径、哈希、风险、预检结果、授权状态和执行结果属于只读事实。
- 用户编辑、语音修改、外部修改、计划版本变化或文件系统状态变化都会使旧 `plan.json`、旧哈希和旧确认失效。
- Markdown 解析失败、字段缺失、操作不在白名单、依赖矛盾、路径越界、冲突策略未明确或语义有歧义时，只生成明确的诊断结果，不生成可执行 `plan.json`，不显示“允许执行”。
- 诊断结果必须指出文档章节、行号或字段、错误原因、影响范围和可供用户选择的修改方向；系统不能替用户选择解决方案。
- 只有用户主动要求生成计划，且草稿通过解析、结构校验、路径检查、文件扫描和预检后，才生成新的 `versions/vNNN/` 冻结版本。
- 任何直接修改 `plan.json`、`result.json` 或冻结版本文档的行为都会造成哈希不匹配并拒绝执行或继续恢复；不得把手改后的 JSON 当作新授权。
- 文档查看、打开、编辑、保存和导出永远不产生授权；授权只能来自独立的确认流程。

##### D.5 本项定稿后的实施约束

- 用户界面默认首先打开执行方案和结果总结，不要求用户阅读日志；高级详情入口才显示 JSON、单项路径和审计关联。
- AI 必须优先通过 `plan_id + plan_version + plan_hash` 查询结构化记录，并以 `result.json`、JSONL 和 SQLite 交叉定位错误；不能只根据 `result.md` 猜测执行事实。
- `result.md` 必须由系统根据 `result.json` 生成，不能由模型自由改写成功/失败状态；人可读建议必须标明“建议”而不是“已执行修复”。
- 计划版本目录必须同时保存 `execution_plan.md`、`plan.json`、`result.md` 和 `result.json`；失败版本不能被新计划覆盖，新计划使用新的版本号并关联前一版本。
- 测试必须覆盖用户层摘要与机器层事实一致、解析失败不生成可执行计划、手改 JSON 被拒绝、失败后 `result.md` 明确提示重新规划，以及 AI 可从 JSONL/SQLite 定位具体失败动作。

#### E. 分级授权、L3 第二重确认与语音播报（交互样式已定稿，状态机细节待定）

已确认：

- 权限确认使用居中模态弹窗；任务结果使用右下角非模态通知。
- 默认主题跟随系统；浅色、深色、高对比度和强调色作为可配置项。
- 权限按钮固定为“允许执行”和“拒绝”，不使用“确定”和“取消”。
- 弹窗使用正式、准确、可审计的语气；至少展示操作类型、风险等级、路径、数量、大小、冲突策略、计划编号和方案状态。
- 权限弹窗出现时进行人物模板语音提醒；用户点击任意按钮后立即停止当前播报；语音不代替弹窗授权。
- L2 点击“允许执行”后完成普通弹窗授权；L3 仍需第二重输入或说出固定短语“确认执行”，并绑定当前计划上下文。
- 任务结果通知默认停留 3 秒，用户可以手动关闭；严重失败和系统拒绝也遵守该规则。
- 任务结果同时使用人物模板进行简短语音播报；完整路径、逐项结果、错误信息、哈希和计划编号保留在通知详情或执行文档中。
- 语音播报保持自然、口语化并符合人物设定；人物称呼、语气和模板属于 `[用户配置]`，不能写死当前个人内容。
- 弹窗、执行方案、执行文档、执行日志和结果记录使用正式语气；人物化表达不得弱化风险、掩盖失败或诱导授权。

仍需明确状态机细节：

- 第一次确认和第二次确认的自然语言提示；
- L3 第二重确认短语固定为“确认执行”，不接受同义词、缩写、追加语气词或模糊识别；
- ASR 同音、口误、低置信度和非完整短语的拒绝与提示方式；
- 普通聊天中的“好、嗯、可以、行”等继续保持无授权含义；
- 确认状态的超时、最大重试次数和失败后的回退；
- 计划被编辑、参数改变、哈希改变、用户取消或播报中断后如何失效；
- 多文件操作是整批确认还是分组/逐项确认；
- 高风险操作是否必须播报固定确认短语“确认执行”；
- 程序重启后确认状态必须失效。

##### G.1 已定稿：启动与会话生命周期

- DeepSeekHarness 是运行时唯一默认主 Agent，Python SDK 是正式运行通道；CLI 只用于人工诊断、测试或用户明确要求的故障恢复。
- 程序启动时只初始化 SDK 适配器并检查配置；第一次收到实际请求时才延迟创建会话，不允许无请求预热。
- 闲聊会话和工作会话必须隔离。闲聊上下文仅在进程内存保留，连续闲置满 30 分钟后销毁，默认不落盘。
- 每项工作任务建立独立会话并绑定 `task_id`；任务完成、取消或失败后关闭，计划、授权状态和工具结果不能直接复用于下一项任务。
- 模式切换时采用最小上下文传递：只传当前明确任务、用户明确引用的内容及完成任务必要的信息，不自动复制完整闲聊历史。
- 每次 Agent 请求使用唯一 `request_id`；工作请求关联 `session_id`、`task_id`，形成计划后再关联 `plan_id` 和 `plan_version`。
- SDK 超时、崩溃、断线或格式错误时立即停止；不自动重试、不自动改用 CLI、不自动切换其他 Agent；已有计划和授权失效，并向用户展示错误原因及可选解决方案。

##### G.2 已定稿：模型与本地安全层硬边界

- 模型只能输出结构化工具调用，不能直接执行自然语言命令；
- 工具注册表、策略引擎和路径守卫必须在模型之外强制校验；
- 模型生成的路径、参数、脚本和 Skill 一律视为不可信输入；
- 模型不能修改黑名单、确认规则、工具白名单和安全配置；
- 建议不能自动变成执行计划；
- 计划中的新增动作必须重新预览、校验并确认；
- 外部网页、文件、API 返回的指令性文本不能直接执行。

#### K. 日志、隐私和历史（存储、保留与可查找性已定稿）

本项的存储位置、默认保留期、审计格式、清理与完整性规则于 2026 年 9 月 15 日确认；密钥脱敏细节、日志级别和用户手动清理交互仍在后续细化。

##### K.1 数据根目录与可发现性

- 所有运行时计划、审计和索引存放在单一、用户可见且可配置的 `data_root`；不得存放在源码仓库、安装目录、系统黑名单目录、`AppData`、系统临时目录、UNC/网络路径或无法可靠解析的链接路径中。
- `[本机配置示例]` 当前已创建的数据根目录为 `<STUDY_ROOT>\AI工作区\voice_assistant_data`；开源版本通过 `data_root: <user-selected-local-directory>` 配置，不得写死该个人路径。
- 设置页必须持续显示完整数据根路径，并提供用户主动触发的“打开数据目录”“复制完整路径”“查看存储与保留规则”入口；打开目录不得由助手擅自触发。
- `data_root` 及其子目录属于助手管理区域：常规文件工具不得移动、删除、覆盖、重命名或整理其中内容；日志与历史清理由专门的保留期策略管理。
- 根目录中的 `README.md` 必须说明完整路径、各目录用途、保留期限、查看方法和手动清理入口；不得含密钥、个人文件正文、原始音频或真实任务内容。

##### K.2 固定目录结构与事实来源

```text
<data_root>/
├─ README.md
├─ audit/YYYY/MM/YYYY-MM-DD.jsonl
├─ plans/<plan_id>/
│  ├─ working/execution_plan.md
│  └─ versions/vNNN/
│     ├─ execution_plan.md
│     ├─ plan.json
│     ├─ result.md
│     └─ result.json
├─ indexes/audit_index.sqlite
└─ temp/audio/
```

- `audit/YYYY/MM/YYYY-MM-DD.jsonl` 是可人工阅读的审计事实来源：每个自然日一个 UTF-8 JSONL 文件，每行一个完整事件；用户可用普通文本编辑器直接查看。
- 审计事件至少记录时间、会话、模式、`plan_id`、`plan_version`、`plan_hash`、`operation_id`、工具名、事件类型、状态、风险等级、授权引用、预检/结果摘要、错误码、正式错误原因和不自动执行的解决建议。
- `plans/<plan_id>/versions/vNNN/` 保存对应版本的人可读 `execution_plan.md`、唯一执行依据 `plan.json`、用户结果总结 `result.md` 和实际结果 `result.json`；审计日志必须通过 `plan_id`、版本、哈希和动作编号精确关联这些文件。
- `indexes/audit_index.sqlite` 仅用于应用内按日期、计划、状态、错误或路径检索；它不是唯一事实来源，损坏或删除后可从 JSONL 和计划版本文件重建。
- `temp/audio/` 仅用于 ASR 必需的临时音频，识别结束即删除，异常情况下最长保留 60 秒；原始音频默认不做持久化。

##### K.3 保留期、聊天边界和审计失败

- 纯闲聊的上下文只保存在进程内存，自最后一次互动起保留 30 分钟；30 分钟空闲、用户手动清空、程序退出或崩溃重启时立即清除。纯闲聊文本、完整 LLM 请求/响应和原始音频默认不写入磁盘，持久化保留期为 0 天。
- 工作模式的审计事件、关联计划版本和结果文件默认保留 180 个自然日；到期后在下一次启动检查或每 24 小时运行检查中清理，最迟不得晚于到期后 24 小时。
- 清理到期记录时，必须联动删除对应的计划历史目录、整日日志文件和 SQLite 索引记录；清理过程只保留删除数量与日期范围的摘要，不重写已经到期的详细内容。
- L2/L3 操作开始前必须成功记录 `operation_started`，结束后必须成功记录最终状态；开始前审计不可写时拒绝执行。动作已开始但程序崩溃或无法写入最终记录时，标记为 `state_uncertain`，不得自动续跑、重试或回滚。

##### K.4 JSONL 完整性提示

- 每条审计事件包含 `previous_event_hash` 与 `event_hash`，构成按顺序的哈希链，用于发现意外截断、删除或修改。
- 哈希链属于异常发现机制，不构成对拥有本机文件权限者的绝对防篡改承诺。
- 发现链条断裂时，记录并展示 `audit_integrity_broken`；历史界面必须明确提示审计记录不完整，助手不得把缺失期间的历史视为完整事实。

仍需明确：

- API key、L3 确认短语相关记录、隐私文件内容和可能保留的 ASR 文本的具体脱敏字段；
- 日志级别、单文件大小与非到期轮转策略；

- 是否允许用户显式导出一份已脱敏的审计历史。
