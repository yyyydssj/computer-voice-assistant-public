# P10 · T1 播报语速「1.4 尾部吞字」根因结案（2026-11-08）

> 结论先行：**不是丢音频，也不是播放丢尾**；是 VoiceStudio 在 `speed>1` 时把**末字的释放（Release）压短**，
> 叠加**单次合成的采样差异**（1.0/1.3 恰好自然、1.1/1.2/1.4 恰好硬收）。补尾静音无效。
> 处置：**默认语速保持 1.0，1.4 不进默认配置**；本轮未改任何代码。

## 1. 背景

- 2026-10-23 新增 `--tts-speed`（默认 1.0，行为不变）：真机 1.4 档计划句 3.67 s → 2.58 s（3.0 → 4.26 字/秒），
  但用户反馈「**尾部吞字 + 轻微发尖**，通常在播报最后几个字」。当时未定性，默认仍是 1.0。
- 10/23 记录给出的下一步探针：同一句用 `--tts-mode http_wav`（整段）与 `ws_pcm` 对比，再用本地 SenseVoice
  回读合成 WAV 的尾字，判断是「音频本身缺内容」还是「播放丢失」。

## 3. 实测事实

### 3.1 传输与播放：都没有丢

| 检查 | 1.0 | 1.4 |
|---|---|---|
| `ws_pcm` 帧完整性 | `done.samples == 收到 PCM/2`（`samples_match=true`） | 同左 |
| `http_wav` | HTTP 200、`audio/wav`、24 kHz/mono/PCM16 | 同左 |
| ASR 回读（SenseVoice） | 「…说确认」 | 「…说确认」（**句尾字都在**） |
| 项目播放栈复播 | 墙钟 **2.05 s**（音频 2.00 s），`COMPLETED` | 墙钟 **1.49 s**（音频 1.48 s），`COMPLETED` |
| 3×200 ms 设备缓冲 | 全部排空后才完成 | 同左 |

⇒ 10/23 剩下的两条假设（引擎截尾 / 播放丢尾）**都被否掉**。

### 3.2 差异在「收尾形态」，不在内容

末尾包络（10 ms 窗，文件末尾往前读）：

| 语速 | 总时长 | 末段衰减（峰值→静音） | 末尾静音 | 最后几个能量级 |
|---|---|---|---|---|
| 1.0 | 1.76 s | **≈60 ms**（自然收尾） | **≈200 ms** | `0.19 → 0.14 → 0.08 → 0.04 → 0.006` |
| 1.4 | 1.48 s | **≈25 ms**（硬停） | **≈100 ms** | `0.156 → 0.066 → 0.026 → 0` |

- F0 中位 1.0 ≈ 245–289 Hz、1.4 ≈ 254–277 Hz（+8% 以内）⇒ 仍不是重采样变调，与 10/23 结论一致。
- 末尾是数字静音，**没有淡出、没有截断**；1.4 的语音完整落在静音之前。

### 3.3 它是「采样差异」，不是速度的单调函数

- 同一句同语速重复合成 **6/6 完全一致**（字节级相同）⇒ 引擎对该（文本、语速）结果是确定的（有缓存）。
- 换 `seed` 会换结果：1.4 + `seed=7` 的末段衰减 **490 ms**、最后能量级 `0.183 → 0.153 → 0.058`，明显更自然；
  1.4 默认 seed 与 `seed=1/42` 都是硬停（≈25–35 ms）。
- 用户真机+离线耳测：**1.0、1.3 结尾正常；1.1、1.2、1.4 突兀**。不是「越快越糟」，而是这批合成样本恰好踩中硬收尾。

### 3.4 补尾静音无效（用户实测）

1.4 音频分别补 150 / 250 / 400 ms 数字静音后用项目播放栈播放：用户确认**仍然突兀**。
原因也就明确了：缺的是**末字本身的释放**，不是后面的空白。

### 3.5 语速改法对照（原型，未采用）

本机有 ffmpeg，用 `atempo`（WSOLA，保音高）对 **1.0 的原始音频**变速：
1.76 s → 1.36 s（1.3）/ 1.26 s（1.4），末段衰减原样保留、不截断。
**用户听感：仍然「太快了，要正常语速」** ⇒ 提速这件事本身不是用户想要的，需求回到「正常语速」。

## 4. 同类项目怎么做（真实来源，2026-11-08 核对）

| 项目 | 做法 | 对我们的意义 |
|---|---|---|
| [xiaozhi-esp32-server](https://github.com/xinnan-tech/xiaozhi-esp32-server)（本机已 clone：`<STUDY_ROOT>\GitHub_pro\xiaozhi-esp32-server`） | 语音链路不设通用语速；各 TTS 渠道用自家参数，例如 `core/providers/tts/edge.py` 里 `edge_tts.Communicate(..., rate=self.edge_rate)` | 引擎原生语速，不动音频 |
| [dsh-gpt-sovits](https://github.com/91koukou/dsh-gpt-sovits)（README 有完整实现说明） | ① 语速用引擎 `speed_factor`（0.5–2.0）；② `fragment_interval: 0` 关掉引擎分段静音，**自己按标点插停顿**（句号 340 ms / 逗号 150 ms / 段落 520 ms）；③ **裁掉每段尾部静音**（从末尾找第一个 `|sample|>0.001`，加 20 ms 余量）；④ 播放倍速靠浏览器 `preservesPitch` | “尾部”是显式在处理，但同样没解决 `speed>1` 的末字释放问题 |
| [hermes-agent issue #6926](https://github.com/NousResearch/hermes-agent/issues/6926) | 明确策略：**引擎有原生 rate 就用原生，没有就 ffmpeg `atempo` 兜底**（Edge/OpenAI 原生；NeuTTS/ElevenLabs 走 atempo） | 业界通行：引擎 1.0 + 本地保音高时间伸缩 |
| [audiotsm](https://readthedocs.org/projects/audiotsm/) | Python WSOLA/OLA 时间伸缩（保音高） | 不依赖 ffmpeg 时的纯 Python 路线 |

## 5. 决定

1. **默认语速保持 1.0，`--tts-speed` 继续是可选实验参数，1.4 不作为推荐值**（与 10/23 处置一致，本次给出根因）。
2. 「播报慢」继续用**缩短文本**解决（D 批次已把计划句 22→11 字、换目标不连播「已取消」），不靠提速。
3. 若以后仍要提速，按同类项目路线：**引擎 1.0 + 句级保音高时间伸缩**（ffmpeg `atempo` 或纯 Python WSOLA），
   而不是引擎 `speed>1`；实施前需单独批次 + 真机听感验收（含变速失真）。
4. 本品 `speed>1` 的「末字硬收尾」属于 **VoiceStudio 引擎侧行为**，不在本仓库修改范围内；
   若哪天必须用 1.4，可考虑「末字质检 + 换 seed 重合成」（`seed=7` 已实测能变自然，但属概率性修补，未采用）。

## 7. 局限与未做

- 只能用 ASR 回读 + 包络/时长指标 + 用户听感交叉验证，没有做逐音节强制对齐（无现成对齐模型）。
- 换 seed 的自然样本只验证到「能变自然」，**没有**做成生产策略（重合成会加延迟，且属概率修补）。
- 本地时间伸缩（atempo/WSOLA）只做了原型听感，用户明确要正常语速后未继续；未接进播放链路。
- 该批探针脚本留在 `%TEMP%`（`tts_*.py`、`play_files.py`），未入库；结论与数据以上表为准。
